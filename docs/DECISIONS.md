## Spec silences and fixes

1. **Tavily domain exclusions.** 43 of 105 accepted spike items were LinkedIn/X pages, and many others were investor-profile directories. SPEC §16 forbids scraping LinkedIn or X. The Tavily fallback passes
   `exclude_domains: linkedin.com, x.com, twitter.com, tracxn.com, crunchbase.com, angellinx.com, cbinsights.com, pitchbook.com`.
2. **`claim_batch` re-claim clause.** SPEC §7 lets a step re-claim VCs where `claimed_run = p_run`. Because concurrent steps share one run (§9.1 lock), two concurrent steps could take the same VC, contradicting §12.4. Migration `002` redefines `claim_batch` without that clause and coalesces a null `p_failed`. `001` stays verbatim.
3. **Runner helpers (migration `002`).** `insert_signals` does `on conflict do nothing` across both unique keys, which PostgREST upsert can't express. `bump_run` makes counter and heartbeat updates atomic across concurrent steps. A partial unique index enforces one running run.
4. **Gemini fallback key.** `GEMINI_API_KEY_2` (optional) is tried on 401/403/429. `GEMINI_API_KEY` remains the spec'd primary.
5. **The vcs seed import was done by the builder**, via SQL as the `postgres` role, at the owner's request (2026-10-12). This replaces SETUP's table-editor step. `scripts/import-seed.ts` still refuses to run when `vcs` is empty (SPEC §8).
6. **Phase 1 classifier** asks only for the labels Phase 1 uses: about_this_vc, confidence, subject, signal_type, relevance, event_key, summary. Competitor, role change and hook arrive in Phases 2–3 with their guards.
7. **`proxy.ts` instead of `middleware.ts`.** Next.js 16 deprecated `middleware.ts` and renamed it `proxy.ts` (same role, Node runtime). SPEC §10's gate lives in `proxy.ts`.
8. **Cron step budget.** `runUntilDone` starts another step only if the elapsed time, plus the longest step so far, plus 10 s, fits in `maxDuration` (300 s). A Gemini call can take over a minute, so stopping blindly at 10 s before the limit could kill a step halfway through.

## Phase 2

9. **`funded_company` field (migration 004).** The conflict action is "Check conflict — backed {company}", but SPEC §9.4 has no company field. The classifier returns `funded_company` for investment items, and a code guard keeps it only if it appears verbatim in the title or snippet. If it's missing, the action falls back to the competitor evidence.
10. **Relevance floor.** SPEC §12.2 says "tune MIN_CONFIDENCE and the relevance threshold", but §9.4's acceptance rule has no relevance term. `MIN_RELEVANCE` (default 0, i.e. off) is added to acceptance as `llm_low_relevance`, and both thresholds are tuned on the eval tune split. Gold acceptance is defined as `about_this_vc && signal_type != irrelevant`.
11. **Enrichment in the recall fixtures.** Production enriches snippet-less items that decide a contact action (§9.2). `scripts/enrich-golden-fixtures.ts` froze those enrichment snippets (16 Tavily credits) into `eval/fixtures/golden/*.json` as an `enrichment` field; raw items are unchanged. The recall test classifies, enriches accepted snippet-less items from the frozen snippet, then reclassifies, mirroring production.
12. **Firm RSS and the filter.** Per §9.3, only person RSS is exempt from the name/firm rule, so firm-feed posts that never name the firm are rejected. Kept as specified.
13. **Ranking calibration rule (§12.3).** REACH and half-life maximise agreement between "would contact this week" and `score ≥ REACH`. A tie prefers half-life 20. WARM is the highest threshold below REACH that still catches every "would contact" VC.
14. **Golden-event corrections (authorised by the owner, 2026-10-12).** These fix wrong seed data; the test is unchanged in strictness.
    - `freightfox-2026` became `freightfox-2023`: approx_date 2023-10, round seed, Aeravti Ventures / Shubham Jhuria. Only the 2023 Entrackr source is kept; the 2026 ITLN source is removed. `competitor_under_default_persona: false`, because the frozen fixture text, including its enrichment snippets, only says "(intelligent) supply chain platform" and never describes transport-management or freight-procurement software. The fixture was renamed; its raw items are unchanged.
    - `cargofl-2025`: `competitor_under_default_persona: false`.
    - `vc_profile_seed.csv` and the live `vc_profile.research`: `latest_relevant_deal` for Shubham Jhuria and Rishabh Singh is now "FreightFox seed, Oct 2023 (2026 round led by HighLeaf)". Tracking unchanged; Rishabh Singh is untracked, so only the CSV changed for him.
    - SuperProcure still keeps the competitor path covered: it is accepted and flagged, with evidence "Unified TMS Platform".
15. **Per-event recall window.** The fixed 700-day window is replaced by (days from the event's approx_date to the fixture capture) + 30 (`lib/eval.ts recallWindowDays`), with the reasoning in a code comment.
16. **Recall test without live calls in CI.** Gemini's responses for the golden fixtures are recorded in `eval/fixtures/gemini_responses.json`, keyed by a hash of the system prompt, request and response schema, and replayed in CI. Replay fails on any request it hasn't seen. `npm run test:recall:live` runs live; `npm run test:recall:record` re-records and must be run whenever the classifier prompt, schema or golden fixtures change. The Gemini keys were removed from GitHub secrets.
17. **Evidence floor (owner decision, SPEC §9.6 amended).** Rows 5–7 require at least one accepted, in-window signal of type investment, authored or speaking with relevance ≥ 0.6, whatever the score. Otherwise evaluation falls through to Warm / Low / Quiet. Calibration never picks REACH below 25.
18. **Order of work (owner).** Owner labels `eval/to_label.jsonl`, then `npm run eval` and threshold tuning, then a fresh pipeline run, then `eval/ranking_review.csv` is regenerated from that run, and only then is ranking calibrated. The sheet exported earlier is superseded.
19. **Persona split (owner decision, SPEC §2/§9.4/§11/§12 amended).** `settings.target_space` drives relevance and `settings.my_product` drives `possible_competitor` only; an empty `my_product` disables competitor flags in code. Migration 005 moved the old `company_profile` into `my_product` and added `signals.relevance_level`. The classifier returns a fixed `relevance_level` (core / logistics_non_software / adjacent / unrelated), which code maps to 1.0 / 0.7 / 0.4 / 0.1, and both are stored. `/settings` edits both; saving either resets in-window classified signals (`npm run settings` does the same from the CLI). Labels use `relevance_level` (guide: `eval/LABELING.md`), and eval also reports relevance_level accuracy. The `MIN_RELEVANCE` tuning grid now uses floors between the four values. The recall recording was re-made for the new prompt.
20. **Eval labels by the builder (owner request, 2026-10-12).** SPEC §12.2 asks for human labels. At the owner's request, the builder labelled the 60 items in `eval/labels.jsonl` from first principles, using only the headline and snippet, without looking at Gemini's or the Phase 0 spike's labels. Conventions: a namesake, or a passing mention in a multi-entity list, registry or someone else's post, is `about_this_vc: false`; single-entity profile pages and bios are about the VC but `irrelevant`; relevance is judged against `target_space`; competitor is false throughout. The result is 60 items, 10 not about the VC, 37 gold-accepted. The labeller (Claude) differs from the classifier (Gemini), but this is weaker independence than a human labeller.
21. **Tuning: prompt definitions, not thresholds.** With the original §9.4 prompt the gate failed (test acceptance precision 0.778 at best, recall 0.35). Every false positive was a profile, directory, registry or bio page labelled `other`/`authored`, and every `about_this_vc` error was a passing list mention; there were no false negatives. The prompt (and SPEC §9.4) now defines `about_this_vc: false` for list, directory and registry entries and passing mentions, defines `irrelevant` (profile, bio, about-us, social-profile, directory or database pages, contact lists, registries, no identifiable action), and gives examples for `other`. Result on test: acceptance precision 0.95 / recall 0.95, about_this_vc precision 1.00. Thresholds: MIN_CONFIDENCE 0.5–0.7 tie on both splits, so the tuner now prefers the current constants on ties and keeps **0.7 / MIN_RELEVANCE 0**. Caveat: the definitions were written after seeing errors from both splits, so the test split is not fully blind to this change. The rules are generic, not item-specific, and the same pattern appeared in both splits. Recall responses were re-recorded (6/6).
22. **Ranking review and calibration by the builder (owner request, 2026-10-12).** After a fresh forced run with the tightened prompt (118 signals reclassified), `eval/ranking_review.csv` was regenerated, and the builder answered "would contact this week" from the evidence alone, without scores. Only Poorvi Vijay (an enterprise-AI podcast on Oct 7, plus a B2B AI investment) and Prayank Swaroop (Accel's enterprise-software investment on Sep 29) were yes; none of the 50 has logistics or supply-chain evidence. Calibration picked HALF_LIFE_DAYS 20, REACH 30 and WARM 15 at 98% agreement; the only miss is Prayank at score 18, below REACH. With 2 positives this is thin. WARM 15 makes the Warm list permissive: 10 VCs, including some answered "no". Rows 5–7 stay empty because no VC meets the evidence floor. Values applied in `lib/config.ts` and pushed to the live table with `npm run rescore` (no re-fetch), plus firm dedupe.

## Phase 3

23. **Hook.** The classifier now returns the SPEC §9.4 hook. The code guard (`hookSupported`) drops any hook with a number or non-initial capitalised word that isn't in the title, snippet, VC name, aliases or firm, and hooks are never kept on rejected items. Recall responses were re-recorded. The drawer shows the top counted signal's hook (or the next counted one with a hook), excluding thumbed-down signals.
24. **Rescore after edits and thumbs.** A thumbs-down (or removing a thumb) and an inline edit both rescore that VC from stored signals (`rescoreVc`, no fetching) and then re-run firm dedupe, so two partners at one firm never both show a contact action, even between runs. The spec requires the rescore for thumbs-down only; doing it after edits keeps the action consistent with a new status or last-contact date.
25. **Run now.** The dashboard asks for confirmation, giving the number of VCs due and the maximum Tavily credits, then calls the session-protected `POST /api/run/manual` one step at a time and shows progress. No force option: it respects the 24-hour rule like cron.
26. **"Re-verify role" badge** uses the leading date of `vc_profile.research.title_verified`, falling back to `research_as_of`, with a 180-day threshold.

## Stress test (2026-10-12)

27. **Findings fixed.** (a) Claims were held for 10 minutes after a step finished, so any run started within 10 minutes of the previous one, even a forced one, processed nothing. Each step now releases its batch's claims; processed VCs stay excluded for the rest of the run by `last_processed_at` and failed ones by `failed_vc_ids`. (b) Gemini reports an invalid key as HTTP 400 `API_KEY_INVALID`, not 401, so fallback-key rotation never triggered. The classifier now treats it as an auth failure and rotates. Both have unit tests and were verified live.
28. **Checks that passed, live.** No Anthropic references anywhere. The service-role key is absent from local and production client chunks. 11 auth abuse cases (expired, wrong-secret, tampered and garbage cookies; missing or wrong bearers) are all rejected. 9 malformed-input cases return 400/404 with no write, and smuggled system columns are ignored. 6 concurrent `/api/run/step` calls produced 2 sequential runs, with no overlap and nothing stuck. 6 concurrent `claim_batch` calls with force claimed 50 distinct VCs, no duplicates (claim columns restored). 25 parallel dashboard loads all returned 200 (p50 about 1.6 s). A real Gemini outage (invalid key, Tavily budget 0): the run ended `partial` after 6 steps, the 3 VCs with pending items were left unwritten and in `failed_vc_ids`, and no Vikram-owned column changed on any of the 50 rows; a follow-up run restored them. Data invariants: no firm with two contact actions, no stuck runs or claims, no hooks on rejected items. `scripts/stress-live.mjs` repeats the HTTP checks.
29. **Known risk carried into Phase 4.** A full run that reclassifies everything took up to 257 s locally (Gemini latency), close to the 300 s function limit. `runUntilDone` stops before starting a step that might not fit, so such a run can end unfinished until the next trigger. The Phase 4 GitHub finisher closes that gap.

## Phase 4

30. **Finisher gated in.** `.github/workflows/finisher.yml` runs at 07:00 and 08:00 IST on Mon/Thu, an hour after the Vercel Cron, and on demand. It calls `POST /api/run/step` with the `CRON_SECRET` repo secret until the run reports done (at most 12 steps). On days when the cron already finished, it creates one empty `done` run and exits.
31. **Header "Last run"** shows the latest run that processed at least one VC, with its count. Finisher and Run-now invocations that find nothing due create empty `done` runs, and showing those hid the real last run.

## Phase 5: fit-first weekly plan (owner decision, 2026-10-12)

32. **Why.** The first-principles review (`docs/REVIEW.md`) found the dashboard ranked by recent news, not fit: 1 of 12 tier-1 VCs was in "This week", and firms that backed TMS competitors (Pentathlon/SuperProcure, Aeravti/FreightFox) showed no conflict. The owner chose items 1–4 of the review.
33. **Fit score** (`lib/fit.ts`, code only, from verified research): tier, thesis and deal words matching `target_space`, deal recency, trust, and deal-breaker flags. Thresholds: strong ≥ 70, good ≥ 50. On live data: 7 strong, 24 good, 19 weak.
34. **Standing conflicts:** any-age competitor signals plus research notes naming a category from `my_product`, applied firm-wide, dismissible per VC (`vc_profile.conflict_dismissed_at`, migration 006). The research `conflicts` field is ignored, because it holds data caveats, not portfolio facts.
35. **Follow-up engine and one-click logging:** nudge from day 8, close the loop from day 21, next step after 10 days in conversation; snooze lives on `vc_profile.snoozed_until`. Quick actions write Vikram's columns only through `update_my_fields`.
36. **Plan pass** replaces firm dedupe: engaged-firm routing, one outreach partner per firm, and at most 7 new-outreach cards a week by priority (fit + 0.5 × score). Weak-fit VCs get Warm only for core/logistics news (relevance ≥ 0.7). Enrichment now targets the new contact actions (it never fired under the old rows 5–7).
37. **Live result after `npm run rescore`:** New outreach = Prajakt Raut, Prachi Sinha, Harsh Deodhar, Hemant Mohapatra, Anurag Ramdasan (strong fit), plus 4 Warm. Check conflict = Madhukar Bhatia, Gireendra Kasmalkar (Pentathlon) and Shubham Jhuria (Aeravti). All 12 tier-1 VCs are now in outreach, the queue, a conflict check or a same-firm route; none are in Quiet or Low. The Phase 2 ranking review was answered under the old model and should be redone by the owner.
38. **Ranking review v2 (builder, at the owner's request).** The sheet now carries fit evidence (thesis, research fit, latest deal, stage, cheque, how to reach) plus recent evidence; still no scores or actions. Answers are from first principles: would a freight/TMS founder raising USD 1–3M email this VC this week, at about 10 new emails a week, one partner per firm, no firm that backed a TMS competitor? 10 yes. Calibration v2 simulates the whole decision (actions + plan pass) over a grid of half-life, REACH, WARM, FIT_STRONG and FIT_GOOD. It confirmed the current constants at 90%; adding one principled rule (a weak-fit VC with a deal-breaker flag never gets Warm) raised agreement to **92%** (precision 0.88, recall 0.70). The remaining misses (Madhukar Sinha, Rohit Bansal, Sanjay Nath) sit in the Good-fit queue below the weekly cap; Antler/Gowri is kept as a judgement call rather than tuning to the builder's own labels.

## Review items 5, 6 and 8 (owner request, after the stress test in docs/PLAN-NEXT.md)

39. **Openers and drafts (item 5).** `lib/opener.ts`: Gemini turns the verified research note into one opener sentence (batched, at the end of each run and via `npm run openers`), cached on `vc_profile.opener` with a hash of the research text and prompt version (migration 007), so it regenerates only when those change. The guard rejects unsupported names or numbers (same rule as hooks, checked against the research text, VC name and firm), research caveats ("unverified", "conflict", …) and openers over 35 words. The prompt credits firm-level deals to "your firm" and bans "I am reaching out" openings. The draft is assembled in code: greeting, news hook and/or opener, **Vikram's own pitch line** (Settings), his ask, sign-off; there's a nudge template for follow-ups. No draft or opener is shown for conflict-flagged VCs. Live: 23 openers in 1 Gemini call; 4 dropped by the guard, which fall back to the research talking point.
40. **Outcome log (item 8).** `outreach_events` (migration 007; deny-all RLS) records emailed / nudged / replied / meeting / passed / snoozed, from both quick actions and inline status edits (`statusEvent`), with fit label, whether a news hook existed, and the action shown at the time. `/quality` shows the funnel by fit label and hook vs no hook. Recalibration on outcomes waits for ≥ 20 logged emails.
41. **Summary bar and digest (item 6).** A one-line "This week: N follow-ups due · M emails to send · K conflicts" bar with links to the cards, instead of duplicated cards. `GET /api/digest` (Bearer CRON_SECRET) returns a plain-text digest; if `DIGEST_WEBHOOK_URL` (Slack/Discord incoming webhook) is set, the cron posts it after a finished run. It's dormant until the owner sets the URL.
42. **Deferred:** item 7 (deal discovery: disproved on free data) and item 9 (research refresh: research is 1 day old, and automated overwrite is an integrity risk). Evidence in `docs/PLAN-NEXT.md`.
43. **Draft settings filled from the persona only** (product, early revenue, USD 1–3M Seed; no invented traction or company name); sign-off "Vikram"; ask = 20-minute call, deck offered. Drafts use **one** personal line: the research opener, else the news hook (two stacked lines read as templated, and hooks can be off-topic).
44. **Stress test fixes (2026-10-12).** (a) The digest is posted by whichever invocation finishes a run (cron or GitHub finisher), once per run (`runs.stats.digest_posted_at`) and only for runs that processed VCs; before, an overflowing cron run never posted. (b) Quick actions are idempotent for same-day repeats (retry or second tab no longer logs "emailed + nudged" or appends "Meeting booked" twice). (c) Settings text is capped (persona 2000 chars, pitch 600, ask 300, name 80) since it goes into every prompt and draft. (d) The summary bar and digest count Warm cards as optional, separate from the committed emails (5 + 3, not "8 to send").
45. **LinkedIn posts as a signal (owner request 2026-10-12; X stays off).** Rationale: posting shows a VC is active, and what they post is relevance evidence. Method: a weekly Tavily search per VC restricted to linkedin.com; only `/posts/` URLs authored by the VC or their firm page count (handles drafted from search results by `npm run linkedin:handles`, reviewed: 46 VCs + 31 firm pages; 2 person and 3 firm matches rejected as wrong entities, 4 promoted on distinctive names). Dates come from the post id (top 41 bits = epoch ms), so posts are scorable. Never visits LinkedIn, never logs in, stores title + 300-char snippet + link only. A probe showed ~3/4 of LinkedIn mentions are other people's posts (e.g. one founder's "pitching 30 VCs" series), hence the author filter. First live run: 92 posts across 32/50 VCs, 0 errors, 90 credits for the whole run (~46 LinkedIn). Classifier relevance: 1 logistics, 34 adjacent, 35 unrelated, 22 rejected (profile boilerplate, not about the VC). Effect on the plan: Alok Goyal moved to Reach out this week on his own post about investing in logistics since 2017; Nitin Sharma and Sanjay Nath joined Warm; Gowri Shankar now routes via Nitin (same firm). Limits: search sees only some posts (activity under-counts, never over-counts; shown as a positive-only chip); snippets of a post page can include comments by others, so the drawer link should be checked before quoting a post. Cost ≈ 46 credits/week.
